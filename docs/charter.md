# プロジェクト憲章

## 1. ゴール

RAG（Gemini Notebook「lp marketing harness」）に蓄積された知識を根拠として、
**売れるLPを作り、運用で売上を伸ばし続けるための全作業をAIで自動化するハーネス製品**を構築する。

「売れる」の定義（暫定・監査人承認待ち）:
- 一次KPI: CVR（成約率）
- 二次KPI: CPA / ROAS / LTV
- ハーネスの成果指標: 「人が作ったLP」または「現行LP」に対するABテストでの勝率・CVR改善幅

## 2. スコープ

| 工程 | 自動化対象 | 人の関与 |
|---|---|---|
| 0. インテーク | 商品・オファー情報の構造化 | 素材提供 |
| 1. リサーチ | 顧客の悩み・競合LP・口コミの収集と分析 | なし |
| 2. 戦略 | ターゲット／USP／訴求軸（複数パターン）の設計 | なし |
| 3. 構成 | セクション構成・情報順序の設計 | なし |
| 4. コピー | FV含む全コピー、訴求軸ごとのバリエーション | なし |
| 5. デザイン・実装 | モバイルファーストのHTML/CSS、画像生成プロンプト | なし |
| 6. 審査 | 原則ルーブリック採点、薬機法・景表法チェック | **公開前承認（必須）** |
| 7. 公開 | デプロイ、計測タグ設置 | なし |
| 8. 運用改善 | 数値分析 → 仮説 → 次のABパターン生成 | 予算・勝ち判定の承認 |

スコープ外（当面）: 広告出稿の自動運用、決済・CRMの構築。

## 3. 役割

- **責任者（Claude）**: 設計・実装・テスト・ドキュメント。各ステップの成果物と「合格基準を満たした証拠」を提出する。
- **監査人（オーナー）**: 各ステップのゲートで成果物を審査し、承認／差し戻しを判断する。RAG（Gemini Notebook）への問い合わせ操作は、API接続が確立するまで監査人が代行する。

## 4. 監査ゲートの運用ルール

1. 各ステップは「目的・成果物・合格基準」を事前に [roadmap.md](roadmap.md) に明記してから着手する。
2. 成果物は PR として提出し、PR本文に合格基準のチェック結果を記載する。
3. やり直せる作業は承認を待たずに進め、結果を PR で示して監査人が事後に修正する（pstack の never-block-on-the-human、ADR-0003）。製品の方向性（前提・欠落の方針・原則の承認・KPI・予算）、やり直せない操作（公開・`main` へのマージ・外部送信・削除）、法令適合の最終判断は監査人の承認を待つ。
4. 設計上の重要な判断は [decisions/](decisions/) に ADR として記録する。
5. **生成物はすべて根拠となる原則IDを保持する**（トレーサビリティ）。「なぜこのコピーか」を原則と出典動画まで遡れること。

## 5. 基本方針

- **RAGが一次情報**: ハーネスが下す判断はRAG由来の原則を根拠とする。LLMの一般知識で補う場合は「RAG外」と明示する。
- **人が最後に責任を持つ箇所を残す**: 公開と法令適合（薬機法・景表法・特商法）は自動化しても最終承認は人。
- **運用前提**: 1本の完璧なLPより、複数パターンを出して検証し続ける仕組みを優先する。
