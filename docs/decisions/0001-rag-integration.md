# ADR-0001: RAG（Gemini Notebook）との接続方式

- ステータス: **提案中（監査人の判断待ち）**
- 日付: 2026-09-26

## 背景

知識源は Gemini アプリ上のノートブック「lp marketing harness」（YouTube動画9本がソース）。
2026年7月に NotebookLM は Gemini Notebook に改称された。

調査結果:
- 一般向け（コンシューマー版）には公式の公開APIがない。
- Enterprise 版にはプレビューAPIがあるが、ノートブックの作成・取得・一覧・共有が中心で、
  チャット問い合わせ（RAG検索）に相当する操作が使えるかは未確認。
- 非公式ライブラリ `notebooklm-py` は問い合わせを含む全機能を扱えるが、
  非公開APIを利用するため仕様変更で壊れるリスクと、利用規約上のリスクがある。

## 選択肢

| 案 | 内容 | 自動化度 | 安定性 | リスク |
|---|---|---|---|---|
| A | **原則カタログ化（蒸留）**: Gemini から原則を構造化して一度抽出し、承認済みのものをリポジトリに保存 | 高（実行時にRAG不要） | 高 | ソース追加時に再抽出が必要 |
| B | Enterprise API | 中〜高 | 高 | ライセンス費用、問い合わせ機能が未確認 |
| C | 非公式 `notebooklm-py` | 高 | 低 | 規約・仕様変更リスク |
| D | 手動ブリッジ: ハーネスが質問を出力し、監査人が Gemini に貼って回答を戻す | 低 | 高 | 人手がボトルネック |

## 提案

**A を主軸、D をフォールバック、B/C は後日評価** とする。

- ソースは動画9本と静的なので、実行時に毎回RAGを叩くより「承認済み原則カタログ」を持つ方が、
  再現性・監査可能性・速度のすべてで優れる。
- 各原則に出典（動画・タイムスタンプ）を持たせることで、RAGの「根拠を辿れる」性質は維持する。
- ハーネス内部は `KnowledgeSource` インターフェース越しに知識へアクセスし、
  将来 B/C に切り替えても工程エージェント側は変更不要にする。

## 監査人に決めてほしいこと

1. 上記方針（A主軸）で良いか
2. Google Workspace / Google Cloud の Enterprise 契約の有無（B の可否）
3. 非公式ライブラリ（C）の利用を許容するか
